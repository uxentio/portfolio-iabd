1. Introducción al Cluster Hadoop¶

Bienvenido a tu entorno de Big Data. Este notebook te guiará por los componentes principales que ya tienes funcionando.

¿Qué es Hadoop?¶

Apache Hadoop es un framework que permite procesar grandes conjuntos de datos utilizando modelos de programación simples en clusters de ordenadores. Está diseñado para escalar desde un único servidor hasta miles de máquinas.

El núcleo de Hadoop consta de dos partes principales:

1. HDFS (Hadoop Distributed File System)¶

Es el sistema de almacenamiento. Imagínalo como un disco duro gigante repartido entre todos los ordenadores del cluster.

  • NameNode (Maestro): Es el bibliotecario. Sabe dónde está cada archivo, pero no guarda los datos reales. Si se cae, perdemos el acceso a todo (por eso es crítico).
  • DataNodes (Esclavos): Son los almacenes. Guardan los bloques de datos reales. En nuestro cluster tenemos 2 DataNodes.

2. YARN (Yet Another Resource Negotiator)¶

Es el sistema operativo del cluster. Gestiona quién usa la CPU y la RAM.

  • ResourceManager: El jefe. Decide cuántos recursos le da a cada tarea.
  • NodeManager: El empleado. Vigila los recursos en cada máquina y reporta al jefe.

1.1 Configuración: Los Archivos XML¶

Hadoop se configura mediante archivos XML. En este entorno, los encontrarás en la carpeta config/ del proyecto. Aquí tienes una explicación rápida de qué hace cada uno para que entiendas la "magia" que ocurre por debajo:

1. core-site.xml (El Núcleo)¶

Define el sistema de archivos por defecto.

  • Propiedad Clave: fs.defaultFS = hdfs://namenode:9000
  • ¿Qué significa?: Le dice a todos los servicios que el "jefe" del sistema de archivos (NameNode) vive en el contenedor namenode y escucha en el puerto 9000.

2. hdfs-site.xml (Almacenamiento)¶

Configura cómo se guardan los datos.

  • dfs.replication = 2: Cada bloque de datos se guarda en 2 sitios distintos (tenemos 2 DataNodes). Si uno falla, el dato sigue vivo en el otro.
  • dfs.permissions.enabled = false: Desactiva la comprobación estricta de permisos para facilitar el aprendizaje en este laboratorio.

3. yarn-site.xml (Recursos)¶

Configura el sistema operativo del cluster.

  • yarn.resourcemanager.hostname = resourcemanager: Indica quién reparte la CPU y RAM.
  • yarn.nodemanager.resource.memory-mb = 1024: Limita a cada nodo a usar máximo 1GB de RAM para tareas. Esto es clave para que el cluster corra en tu portátil sin colapsarlo.
  • yarn.scheduler.minimum-allocation-mb = 256: Define el tamaño mínimo de un contenedor. Importante para que tareas pequeñas no desperdicien RAM.

4. mapred-site.xml (Cómputo)¶

Define cómo se procesan los datos.

  • mapreduce.framework.name = yarn: Le dice a Hadoop que use YARN para gestionar las tareas de MapReduce, en lugar del modo antiguo.

Ejercicios prácticos: Operaciones básicas en HDFS¶

Todos los ejercicios se deben ejecutar como usuario root en el contenedor del NameNode. Para cambiar al usuario root, ejecuta:

# No need to switch user, running as root

Ejercicio 1: Exploración de directorios¶

Explora la estructura de directorios en HDFS usando los siguientes comandos:

# Listar el contenido del directorio home de root
hdfs dfs -ls

# Listar el contenido del directorio raíz /
hdfs dfs -ls /

# Listar el contenido del directorio /tmp
hdfs dfs -ls /tmp

# Listar directorios con información detallada (tamaño, permisos, etc.)
hdfs dfs -ls -h /user

Ejercicio 2: Crear directorios¶

Crea una estructura de directorios en HDFS bajo tu directorio home:

# Crear un directorio llamado "datos"
hdfs dfs -mkdir datos

# Crear un subdirectorio "datos/entrada" (requiere que "datos" exista)
hdfs dfs -mkdir datos/entrada

# Crear múltiples directorios de una vez con -p (crea padres si no existen)
hdfs dfs -mkdir -p datos/procesados/resultados

# Verificar que se han creado correctamente
hdfs dfs -ls -R datos

Ejercicio 3: Crear archivos de prueba¶

Crea algunos archivos de texto para practicar:

# Crear un archivo local de prueba
echo "Este es el contenido del archivo 1" > /tmp/archivo1.txt
echo "Contenido del archivo número 2" > /tmp/archivo2.txt

# Copiar archivos locales a HDFS
hdfs dfs -put /tmp/archivo1.txt datos/entrada/
hdfs dfs -put /tmp/archivo2.txt datos/entrada/

# Crear un archivo directamente en HDFS usando echo (a través de una tubería)
echo "Archivo creado directamente en HDFS" | hdfs dfs -put - datos/archivo_directo.txt

# Verificar los archivos creados
hdfs dfs -ls datos/entrada/
hdfs dfs -ls datos/

Ejercicio 4: Ver el contenido de archivos¶

Lee el contenido de los archivos que has creado:

# Ver el contenido de un archivo (similar a cat en el sistema local)
hdfs dfs -cat datos/entrada/archivo1.txt

# Ver el contenido de múltiples archivos
hdfs dfs -cat datos/entrada/archivo1.txt datos/entrada/archivo2.txt

# Ver el contenido con más detalle (muestra también el número de líneas)
hdfs dfs -cat datos/archivo_directo.txt | wc -l

# Ver solo las primeras líneas de un archivo
hdfs dfs -cat datos/entrada/archivo1.txt | head -n 5

Ejercicio 5: Copiar y mover archivos¶

Practica copiando y moviendo archivos dentro de HDFS:

# Copiar un archivo a otra ubicación
hdfs dfs -cp datos/entrada/archivo1.txt datos/copia_archivo1.txt

# Mover un archivo a otro directorio
hdfs dfs -mv datos/copia_archivo1.txt datos/procesados/

# Verificar que el archivo se ha movido
hdfs dfs -ls datos/procesados/
hdfs dfs -ls datos/entrada/

Ejercicio 6: Información sobre archivos y directorios¶

Obtén información detallada sobre archivos y directorios:

# Ver el tamaño total de un directorio
hdfs dfs -du -h datos/

# Ver el tamaño de cada archivo dentro de un directorio
hdfs dfs -du -h -v datos/entrada/

# Contar el número de archivos en un directorio
hdfs dfs -ls -R datos/ | grep "^-" | wc -l

# Ver información detallada de un archivo específico
hdfs dfs -ls -l datos/entrada/archivo1.txt

# Ver el espacio total usado y disponible en HDFS
hdfs dfsadmin -report | grep "Configured Capacity\|DFS Used\|DFS Remaining"

Ejercicio 7: Cambiar permisos y propietarios¶

Trabaja con permisos de archivos en HDFS:

# Cambiar permisos de un archivo (modo octal)
hdfs dfs -chmod 644 datos/entrada/archivo1.txt

# Ver los permisos actuales
hdfs dfs -ls -l datos/entrada/

# Cambiar permisos de un directorio y su contenido recursivamente
hdfs dfs -chmod -R 755 datos/

# Cambiar el propietario de un archivo (requiere permisos de admin)
# hdfs dfs -chown root:root datos/entrada/archivo1.txt

Ejercicio 8: Comparar archivos locales y en HDFS¶

Compara un archivo local con uno en HDFS:

# Ver el contenido del archivo local
cat /tmp/archivo1.txt

# Ver el contenido del archivo en HDFS
hdfs dfs -cat datos/entrada/archivo1.txt

# Descargar un archivo de HDFS al sistema local
hdfs dfs -get datos/entrada/archivo1.txt /tmp/descargado.txt

# Comparar los dos archivos
diff /tmp/archivo1.txt /tmp/descargado.txt

Acceso a HDFS desde python con pyarrow¶

PyArrow proporciona una interfaz Python para interactuar con HDFS a través de su módulo pyarrow.fs.HadoopFileSystem. Esto nos permite realizar operaciones sobre HDFS directamente desde Python sin necesidad de usar comandos de shell.

Como usuario root en el contenedor namenode, ejecuta los siguientes pasos:

# Activar el entorno virtual
source ~/.venv/bin/activate
  1. Instalar PyArrow:
# Con el entorno virtual activado

  1. Configurar las variables de entorno para Hadoop:
export CLASSPATH="$(hadoop classpath --glob):$CLASSPATH"
  1. Verificar la instalación:

def copy_file_hdfs(hdfs_fs, src, dst):
    """Copia un archivo en HDFS de src a dst"""
    with hdfs_fs.open_input_stream(src) as f_in:
        with hdfs_fs.open_output_stream(dst) as f_out:
            f_out.write(f_in.read())

Ventajas de usar PyArrow para HDFS¶

  • Integración nativa: Conexión directa con HDFS sin necesidad de comandos shell
  • Formato Parquet: Lectura/escritura eficiente de datos columnares
  • Rendimiento: Operaciones optimizadas en C++ subyacente
  • Portabilidad: Mismo código funciona con diferentes sistemas de archivos (HDFS, S3, local)
  • Pythonic: API orientada a objetos más natural para desarrolladores Python

Notas importantes¶

  • Conexión HDFS: Usar host='namenode' y port=9000 (configurado en core-site.xml). PyArrow permite también un caso especial con hdfs://default:0, para que el código funcione en cualquier entorno Hadoop una vez que PyArrow tiene acceso a la configuración de Hadoop.
  • Usuario: Especificar user='root' para mantener permisos consistentes
  • Rutas: Siempre usar rutas absolutas (comenzando con /)
  • Tipos de archivo: PyArrow distingue entre FileType.File, FileType.Directory, y FileType.NotFound
  • Encoding: Recordar codificar/decodificar strings a bytes cuando sea necesario

1.1 ¿Qué es Spark y su Historia?¶

Apache Spark nació en la Universidad de Berkeley (AMPLab) para solucionar las grandes limitaciones de Hadoop MapReduce. MapReduce era excelente, pero muy rígido: escribía datos a disco constantemente, lo que lo hacía terrible para tareas interactivas o algoritmos iterativos (como el Machine Learning).

Spark trajo una revolución al ofrecer un motor unificado de computación distribuida. En lugar de tener una herramienta para cada cosa, Spark permite en un solo motor:

  • Procesamiento Batch (por lotes nocturnos, etc.)
  • Consultas Interactivas (mediante SQL y DataFrames)
  • Streaming (Procesamiento en tiempo real con Structured Streaming)
  • Machine Learning e Ingeniería de Grafos

Todo esto procesando principalmente en Memoria RAM, consiguiendo velocidades hasta 100 veces mayores.

🚀 Introducción a Apache Spark sobre Hadoop¶

¡Bienvenido a este cuaderno introductorio! En los cuadernos anteriores aprendimos sobre el ecosistema Hadoop y cómo HDFS nos permite almacenar grandes volúmenes de datos de forma distribuida.

Hadoop originalmente utilizaba un motor de procesamiento llamado MapReduce. Sin embargo, MapReduce tiene varias limitaciones, principalmente porque lee y escribe constantemente en disco entre las diferentes fases del mapa (map) y la reducción (reduce). Esto lo hace lento para muchos tipos de tareas analíticas.

Aquí es donde entra Apache Spark.

🥊 Hadoop (MapReduce) vs Apache Spark¶

Spark no es un reemplazo de todo Hadoop, de hecho, se lleva de maravilla con HDFS y YARN. Spark vino a reemplazar principalmente a la parte de procesamiento: MapReduce.

Característica Hadoop (MapReduce) Apache Spark

Vamos a inicializar nuestra sesión de Spark. Esta es la puerta de entrada a todas las funciones.

1.4 Componentes Core de Spark¶

Para entender cómo Spark procesa los datos, es vital conocer sus componentes principales. Aunque en esta sesión usemos un entorno simplificado, la teoría es la misma para clústeres gigantes.

  1. Spark Driver (El Director):

    • Es el cerebro de la aplicación Spark.
    • Analiza, planifica y distribuye el trabajo (tareas).
    • Mantiene el estado de la aplicación y presenta la interfaz web (Spark UI).
    • En nuestro laboratorio: El Driver se ejecuta directamente dentro de este entorno de Jupyter Notebook.

  2. Spark Executors (Los Trabajadores):

    • Son los procesos que realmente ejecutan el código y procesan los datos.
    • Reciben instrucciones del Driver, ejecutan las tareas y devuelven los resultados.
    • También almacenan datos en memoria (caché) para que el procesamiento sea rápido.
    • En nuestro laboratorio: Se ejecutan como hilos (threads) dentro del mismo contenedor de Jupyter.

  3. Cluster Manager (El Gestor de Recursos):

    • Es el encargado de asignar recursos (CPU, memoria) a las aplicaciones Spark.
    • Spark es agnóstico al gestor; puede usar YARN (de Hadoop), Kubernetes, Apache Mesos, o su propio Standalone Cluster Manager.
    • En nuestro laboratorio: No usamos un Cluster Manager externo. Usamos el Modo Local de Spark, que simula todo un clúster en un solo proceso.

1.5 Modo Local vs. Clúster Distribuido¶

Spark puede ejecutarse en diferentes modos dependiendo de la infraestructura y el objetivo. Es crucial entender la diferencia.

Característica ⚡ Modo Local (Nuestro Laboratorio) ☁️ Clúster Distribuido (Producción)
Ubicación de Procesos Driver y Executors corren en una única máquina (o contenedor). Driver corre en un nodo, Executors corren distribuidos en múltiples nodos.
Gestión de Recursos Spark mismo gestiona sus hilos. No requiere un sistema externo. Requiere un Cluster Manager (YARN, K8s) para orquestar contenedores/procesos en distintas máquinas.
Paralelismo Limitado por los núcleos de la máquina local (ej. local[*] usa todos los cores lógicos disponibles). Escala horizontalmente: si añades máquinas al clúster, añades más núcleos y RAM para paralelizar.
Fallo de Nodos Si el proceso falla, la aplicación entera muere. Tolerancia a fallos real: si un nodo (Executor) cae, el Driver reasigna esa tarea a otro nodo sano.
Uso Principal Desarrollo, pruebas, aprendizaje, y procesamiento de datos pequeños/medianos que caben en una máquina. Procesamiento de Big Data real (Terabytes/Petabytes) en entornos de producción.
Ventaja principal Simplicidad y ligereza. Cero configuración de red, arranca al instante y consume poca RAM base. Escalabilidad masiva. Puede manejar volúmenes de datos que ninguna máquina sola podría soportar.

💡 Nota importante: El código que escribes en PySpark es idéntico en Modo Local y en Clúster Distribuido. Spark abstrae la infraestructura. Puedes desarrollar y probar tu código aquí, y luego llevarlo a un clúster de producción con cientos de máquinas sin cambiar tu lógica.

1.6 APIs de Spark: Bajo vs Alto Nivel¶

A lo largo de su evolución (desde 2014 hasta hoy), la forma de programar en Spark ha cambiado drásticamente.

  1. API Estructurada (Alto Nivel): DataFrames y SQL

    • Es el estándar absoluto hoy en día (Spark 3.x y 4.x).
    • Un DataFrame es como una tabla estructurada (filas y columnas), muy similar a usar la librería pandas o escribir sentencias SQL.
    • Ventaja: Spark sabe qué estructura tienen los datos y tiene un optimizador interno mágico llamado Catalyst que reescribe tu código para que vuele.
    • Casos de uso: El 95% del tiempo. Transformaciones, ETL, lectura/escritura de HDFS/Parquet/CSVs.

  2. API no estructurada (Bajo Nivel): RDDs (Resilient Distributed Datasets)

    • Es la estructura original de Spark. Colecciones de código distribuido sin estructura definida (orientado a objetos).
    • Ventaja: Tienes el control absoluto de bajo nivel sobre cada registro y partición.
    • Desventaja: Spark no puede optimizarlo tan bien como un DataFrame, y es más engorroso de programar.
    • Casos de uso: Rara vez (5%). Solo si trabajas con estructuras sumamente exóticas o lógicas mega-personalizadas que no encajen en una tabla.

1.7 El Cerebro de la Ejecución Distribuida¶

Para entender por qué tu código vuela o por qué colapsa la memoria, es clave entender este vocabulario:

  • Job (Trabajo): La gran tarea completa que Spark debe hacer (ej: "Lee este Parquet, agrúpalo y guarda el resultado").
  • Stage (Etapa): Spark divide un Job en sub-etapas. ¿Cuándo corta una etapa y empieza otra? Cuando ocurre un Shuffle (es decir, cuando los Nodos/Executors necesitan pasarse datos por red entre ellos, como en un gran GROUP BY).
  • Task (Tarea): La unidad más pequeña de trabajo. Un Executor ejecuta una Task sobre una Partición de datos. ¡A más particiones, más tareas paralelas!
  • DAG (Grafo Acíclico Dirigido): Es el mapa estricto de pasos que Spark dibuja internamente antes de ejecutar nada para calcular la ruta más óptima.
  • Dependencia Estrecha (Narrow): Una tarea necesita datos que ya están en el mismo nodo (Rápido ⚡).
  • Dependencia Ancha (Wide): Una tarea necesita datos esparcidos por varios nodos, obligando a mover datos por la red (Shuffle - Lento 🐢).

Explicación¶

print(df.rdd.getNumPartitions())¶

  • Devuelve el número actual de particiones del DataFrame.

  • En Spark, las particiones son “trozos” de datos que se procesan en paralelo.

  • Si tienes muy pocas, no aprovechas los cores.

  • Si tienes demasiadas, hay overhead (muchas tareas pequeñas).

df = df.repartition(16)¶

  • Fuerza al DataFrame a tener 16 particiones.

  • Esto puede mejorar rendimiento en operaciones posteriores (groupBy, join, etc.) si 16 encaja mejor con tu máquina.

  • Ojo: repartition() suele implicar shuffle (mueve datos entre particiones), así que no conviene usarlo sin necesidad.

Cuándo usarlo¶

  • ✅ Antes de operaciones pesadas si ves mala distribución / pocas particiones.

  • ✅ Si quieres ajustar el paralelismo en local (por ejemplo 8, 16, 32).

  • ❌ No lo uses en cada paso del pipeline, porque el shuffle cuesta tiempo.

Explicación fácil (qué hace cada cosa)¶

local[*]¶

Usa todos los núcleos de tu computador.
➡️ Más paralelo = mejor uso de tu CPU.

spark.driver.memory = 8g¶

Le da memoria a Spark.
➡️ Si tienes poca memoria, Spark va lento o puede fallar.

spark.sql.shuffle.partitions = 16¶

Controla cuántas particiones usa Spark en operaciones pesadas (groupBy, join, etc.).
➡️ En local, 16 suele ir mejor que 200 (que muchas veces es demasiado).

df.rdd.getNumPartitions()¶

Te dice cuántas particiones tiene el DataFrame.
➡️ Sirve para entender si estás usando pocas o demasiadas.

df.repartition(16)¶

Reorganiza los datos en 16 particiones.
➡️ Ayuda a repartir mejor el trabajo, pero cuesta (shuffle).

persist(MEMORY_AND_DISK)¶

Guarda el DataFrame para reutilizarlo varias veces.
➡️ Evita recalcular todo desde cero en cada operación.

Regla fácil para recordar¶

  • Explorar rápido → usa muestra (sample)

  • Operaciones pesadas → revisa particiones

  • Repetir análisis → usa cache/persist

  • Velocidad de lectura → usa Parquet

🚨 Caso 3: Cambio de Esquema Silencioso y Corrupción¶

(Ref. Teórica UT3 - 4.3 Ejemplo 3: Cambio de esquema silencioso)

Problema: En origen, siempre enviaban el peso del paquete como número. Una actualización en su App sin avisarnos ahora lo envía como texto ("14 Kg"). Si usamos lecturas relajadas (como CSV con inferSchema=True), Spark intentará parsear "14 Kg" y al fallar matemáticamente, escribirá Null sin detener el Job. ¡Basura entra, Basura sale!
